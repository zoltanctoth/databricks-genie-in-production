1. Principals and profiles

A principal is anything that can hold a permission: a user, a service principal, or a group. Every Databricks action is performed as exactly one principal, and that principal is decided before the first API call by the CLI's authentication resolution. Most of the confusion on 2026-10-02 came from not knowing which principal a command ran as.

PrincipalIdentified byAuthenticates withProfile auth_typeHere

Service principals are addressed by application ID everywhere in configuration: in GRANT … TO `47d22b7a-…`, in a bundle's run_as.service_principal_name, and in grants.principal. The display name you gave it in the admin console is only a label.

Profiles are named credential sets

A profile is one section in ~/.databrickscfg: a host plus a way to get a token. The CLI picks one by this order, and the first match wins:

  1. Environment variables such as DATABRICKS_HOST, DATABRICKS_CLIENT_ID, DATABRICKS_CLIENT_SECRET, DATABRICKS_TOKEN.
  2. The profile named by --profile or DATABRICKS_CONFIG_PROFILE.
  3. The [DEFAULT] profile.

2. Two permission systems, two YAML keys

Databricks has two unrelated access-control systems and a bundle talks to both. Mixing them up is the single most common source of "but I granted that" confusion.

Workspace access controlUnity Catalog privileges
Protectsworkspace objects: jobs, pipelines, apps, notebooks, warehouses, and service principals themselvesdata objects: catalog, schema, table, view, volume, function, model
Vocabularylevels: CAN_VIEW, CAN_RUN, CAN_MANAGE_RUN, CAN_MANAGE; on a service principal: CAN_USE ("Service Principal User")privileges: USE CATALOG, USE SCHEMA, SELECT, MODIFY, CREATE TABLE, CREATE MATERIALIZED VIEW, READ VOLUME, WRITE VOLUME, CREATE SCHEMA, MANAGE, ALL PRIVILEGES
Set bythe object's Permissions dialog, the Permissions APIGRANT … ON … TO … in SQL, Catalog Explorer, the Grants API
Bundle keypermissions: at top level or per target, applied to every resource the bundle deploysgrants: on a catalogs, schemas or volumes resource. There is no top-level grants.
Inherits?no, per object (folder ACLs aside)yes, downward: a grant on the catalog applies inside every schema, a grant on the schema applies to every table and volume in it
Ownershipcreator owns; owner has CAN_MANAGEcreator owns; owner holds every privilege, may grant, may transfer with ALTER … OWNER TO

The two gateway privileges

Unity Catalog requires a path to the object, not only a privilege on it. To read genie_reference.prod.dim_listing a principal needs USE CATALOG on the catalog, USE SCHEMA on the schema, and SELECT on the table (or inherited from above). Owning the schema does not grant USE CATALOG on its parent, which is exactly why the service principal in this repo gets one catalog-level grant and nothing more there.

Ownership rules that bite in bundles

  • A schema resource is always owned by the deploying identity. run_as is ignored for schemas. So the deployer never needs grants on its own schemas, and the run identity always does.
  • Whoever runs CREATE CATALOG owns the catalog. On 2026-10-02 that was you in the UI, so the service principal had nothing, hence the 403.
  • Only an owner, a MANAGE holder, the parent's owner, or a metastore admin may grant. A bootstrap script that runs as the service principal cannot grant the service principal anything. One that runs as the catalog owner can.

4. Least privilege, concretely

Least privilege means every identity holds only the privileges its job needs, at the narrowest object that still works. In this project it splits into three jobs:

JobIdentityNeedsGets it how
Create the shared catalogyouCREATE CATALOG on the metastoreworkspace admin by default; one-time, by hand or by the bootstrap SQL
Deploy a targetyou (or CI)USE CATALOG + CREATE SCHEMA on the catalog; CAN_USE on the service principal it will name in run_ascatalog owner has them already; CAN_USE is a role you add to yourself on the SP
Run prod jobs and the pipelineservice principalUSE CATALOG on the catalog; on prod_raw: USE SCHEMA, READ VOLUME, WRITE VOLUME; on prod: USE SCHEMA, CREATE TABLE, CREATE MATERIALIZED VIEW, SELECT, MODIFYcatalog grant from bootstrap.yml; schema grants from the prod target override

What the service principal deliberately does not get: CREATE SCHEMA (it never deploys), anything on the dev schemas (it never runs there), ALL PRIVILEGES anywhere, and ownership of anything. If the prod pipeline is compromised or misconfigured, the blast radius is two schemas.

Why not let the SP own everything? It works, and setup B in the session did exactly that. The cost is that the SP then needs CREATE SCHEMA, owns prod objects that humans cannot see without further grants, and becomes a single identity that both deploys and runs, which is the thing audit teams ask you to separate.

5. Dev and prod in one workspace

Two common layouts. Both isolate dev from prod; they differ in where the boundary sits and in what the bundle may own. Switch between them.

How it works

  • Isolation boundary is the catalog. Dev and prod cannot see each other without an explicit cross-catalog grant.
  • Same schema names in both; only var.catalog changes per target. Code never mentions the environment.
  • Two catalogs to create by hand on a Default Storage workspace, two USE CATALOG grants, each scoped to its own environment.
  • Catalogs still stay out of the bundle: each is shared by nothing, but the API cannot create them here, and a destroy of a target would otherwise delete a whole catalog.

Bundle sketch

variables:
  catalog: { default: genie_dev }
targets:
  dev:
    mode: development
  prod:
    mode: production
    variables: { catalog: genie_prod }
    run_as: { service_principal_name: 47d22b7a-… }

How it works

  • Isolation boundary is the schema. The catalog is shared infrastructure with a lifetime longer than any target.
  • Each target owns only its own schemas, so bundle destroy -t dev removes dev_raw and dev and nothing else.
  • One catalog to create by hand, one USE CATALOG grant. The SP's schema grants are declared in YAML and reach only prod_raw and prod.
  • Price: schema names carry the environment (dev, prod), so var.schema differs per target instead of var.catalog.

Why the catalog must not be a shared resource

Each target keeps its own state file listing what it created. If both targets declared resources.catalogs.genie_reference, the second deploy fails with "already exists", and if you got past that, bundle destroy -t dev would delete the catalog together with every prod table in it. A target should own only objects whose lifetime equals the target's.

6. Deployment modes

mode is optional. It is a bundle of defaults applied at deploy time, nothing more, and each default can be overridden with presets. The behaviors below are quoted from the deployment-modes page, last updated 2026-09-11.

Try it · development prefix

The prefix is [dev ${workspace.current_user.short_name}], the part of your email before the @, with dots and such kept.

run_as, precisely
  • Deployer is the identity behind the CLI call. It uploads files, creates jobs, pipelines and schemas, and owns the schemas.
  • Runner is run_as. Jobs and pipelines execute as it. It must exist, be an application ID, and the deployer needs CAN_USE on it.
  • When deployer and runner differ, only jobs and pipelines are supported under run_as. Model serving endpoints refuse it.
  • Deployment mode never changes who deploys. It changes names, flags and validations.

8. The four errors of 2026-10-02

Each one is a lesson about a different layer. Read them as a checklist for the next workspace.

1
cannot create resources.catalogs.genie_reference: Metastore storage root URL does not exist. Default Storage is enabled in your account.

Layer: storage. The metastore has no storage root, and only serverless workspaces may create catalogs on Default Storage from SQL or the API. A classic workspace must use the Catalog Explorer dialog. Consequence for the design: the catalog is created by hand and is not a bundle resource.

2
bootstrap printed "state": "FAILED" and then kept going into bundle deploy

Layer: shell. The statement execution API returns HTTP 200 for a failed statement, so set -e saw success. The script now reads the body and stops with a message pointing at the manual step.

3
User does not have CREATE SCHEMA and USE CATALOG on Catalog 'genie_reference'. (403 PERMISSION_DENIED)

Layer: identity. "User" was the service principal, because exported environment variables outrank the profile file. You owned the catalog from step 1, it had nothing. The fix was not a grant but choosing who deploys: pass --profile genie-prod-me, so the catalog owner deploys and the SP only runs.

4
missing property: name (editor, twice)

Layer: tooling. The editor validates a target override block against the full resource schema, where name is required. The CLI merges overrides onto the base first and is happy. Repeating name and catalog_name in the override satisfies both.
