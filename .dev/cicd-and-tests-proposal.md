# CI/CD and test design (decided 2026-10-08)

Status: implemented 2026-10-08 (`.github/workflows/pr.yml`, `main.yml`, `release.yml`, `bundle/resources/tests.job.yml`), awaiting review; not yet run on GitHub. Purpose is instructional: the smallest CI/CD that still teaches validation, integration testing and promotion. Sign-in uses an OAuth client secret until an account admin creates the two federation policies (decided 2026-10-08: the author's login reaches only the account console's workspace picker, so it is not an account admin).

## Flow

| Trigger | GitHub environment | Workflow | What runs | What it teaches |
|---|---|---|---|---|
| Pull request to `main` | `ci` | `pr.yml` | `bundle validate --strict -t dev` and `-t prod`; `bundle plan -t prod` written to the job summary | Catch config errors and see the blast radius before merge |
| Push to `main` (merge) | `ci` | `main.yml` | `bundle deploy -t dev`, then `bundle run` of `airbnb_pipeline`, `deploy_metric_views`, `tests` | Integration tests on real data in an isolated copy |
| Push to `release` (merge) | `prod` | `release.yml` | `bundle deploy -t prod`, then the same three runs as a smoke test | Promotion; prod deployed only by the service principal |

Promotion: a pull request from `main` to `release` (students see the prod plan once more), with `release` protected so nothing lands there any other way.

## Authentication

### Now: OAuth M2M with a client secret

- An OAuth secret for the service principal, generated by a workspace admin under workspace Settings > Identity and access > Service principals > `dab_principal` > Secrets. **[verify]** that the tab offers secret generation for this service principal.
- Stored as GitHub environment secret `DATABRICKS_CLIENT_SECRET` in both `ci` and `prod` (for example `gh secret set DATABRICKS_CLIENT_SECRET --env ci`, which prompts for the value). Job env: `DATABRICKS_HOST`, `DATABRICKS_CLIENT_ID` (variables), `DATABRICKS_CLIENT_SECRET` (secret). No `id-token: write` needed.
- Secrets expire; note the expiry date and rotate. The `prod` environment's branch rule still limits the prod secret to `release`.

### Target: workload identity federation


- CLI: `databricks/setup-cli@v1.19.0` (matches the local CLI). Job env: `DATABRICKS_AUTH_TYPE: github-oidc`, `DATABRICKS_HOST` and `DATABRICKS_CLIENT_ID` from GitHub environment variables (not secrets). Workflow `permissions: id-token: write, contents: read`.
- One service principal, the existing prod one (`47d22b7a-…`), with two federation policies (account admin, `databricks account service-principal-federation-policy create`), issuer `https://token.actions.githubusercontent.com`:
  - `repo:zoltanctoth@445752/databricks-genie-in-production@1400199154:environment:ci`
  - `repo:zoltanctoth@445752/databricks-genie-in-production@1400199154:environment:prod`
- The repository was created 2026-10-01, after GitHub's 2026-07-15 switch, so its `sub` claim uses the immutable format with numeric owner and repository IDs (confirmed through `GET /repos/.../actions/oidc/customization/sub` on 2026-10-08). The `repo:<org>/<repo>:environment:prod` example in the Databricks docs would not match.
- The `prod` GitHub environment is restricted to the `release` branch (deployment branch rule). That is the security boundary: only code on `release` can obtain a token matching the prod policy.
- Hardening left as a course note: a separate CI service principal so CI can never write prod schemas.

## Tests

1. **PR (static):** `bundle validate --strict` for both targets. Optional later: a pytest that parses the YAML in `src/metric_views/*.sql` and checks every dimension and measure has `comment`, `display_name` and `synonyms`.
2. **Main (integration):** the pipeline and the metric view job finish successfully. That alone catches the pipeline rejecting metric view DDL or broken quoting.
3. **Main (integration) and release (smoke):** the `tests` job (`resources/tests.job.yml`, SQL task on the warehouse) (`src/tests/gold_and_metric_views.sql`) with 14 `assert_true()` checks: gold row counts, no orphan foreign keys, every gold column commented, the 2026-10-05 acceptance checks against Inside Airbnb's published estimates, and `MEASURE(availability_ratio)` by neighbourhood equal to a hand-written `AVG` over `fact_calendar`. Passed on dev 2026-10-08 (61 s).
4. **Out of CI:** Genie benchmarks and `mlflow.genai.evaluate` (cost, non-deterministic); run by hand or on a schedule later.

## Findings from the local dry run (2026-10-08, as the service principal via profile `genie-prod-sp`)

- **Resolved [verify]:** the dev target deployed by the service principal gets clean names: `dev_dab_principal_raw`, `dev_dab_principal_airbnb`, jobs `[dev dab_principal] ...`, root `/Workspace/Users/47d22b7a-…/.bundle/.../dev`. The service principal has `CREATE_SCHEMA` and `USE_CATALOG` on `genie_reference` and `CAN_USE` on the warehouse through `users`.
- `bundle validate --strict` passes for both targets; `bundle plan -t prod` shows prod already has an earlier deploy (pipeline, schemas, volumes unchanged) and the first release adds the three jobs and the `WRITE_VOLUME` grant (6 add, 2 change, 0 delete).
- Local dry runs must use a clean copy without `bundle/.databricks/`: the CLI otherwise reuses the developer's local state and tries to read `dev_tothz_*` as the service principal (403). CI runners start clean.
- **Open: `setup_workspace` fails as the service principal** with `User does not have permission SELECT on any file`. Reading a raw `s3a://` path outside a UC external location needs the legacy `SELECT ON ANY FILE` privilege, which workspace admins have and the service principal lacks. The first release would fail the same way (prod volumes are empty). Options: grant `SELECT ON ANY FILE` to the service principal (one statement, broad privilege), or rewrite the setup notebook to download over public HTTPS (`https://dbx-data-public.s3.amazonaws.com/...`) so no file privilege is needed.
- `bundle deploy` in CI fails on destructive changes (no prompt, no `--auto-approve`). Intended: a delete or recreate stops the run and needs a human.
- The `WRITE_VOLUME` grant for the service principal on the prod raw schema is added in `databricks.yml`.

## Implementation order

1. Generate the service principal OAuth secret (workspace admin).
2. GitHub environments `ci` and `prod` with variables `DATABRICKS_HOST`, `DATABRICKS_CLIENT_ID` and secret `DATABRICKS_CLIENT_SECRET`; `prod` restricted to `release`; branch `release` created and protected.
3. Resolve the `setup_workspace` file privilege (see findings).
4. Run `pr.yml` by manual trigger to prove sign-in, then merge to `main` (`main.yml`).
5. Create `release` from `main`: the first `release.yml` run is the prod first deploy.
6. (done) Workflows, `tests` job and `WRITE_VOLUME` grant written.
7. Later: an account admin creates the two federation policies; switch each workflow's `env` block to `DATABRICKS_AUTH_TYPE: github-oidc`, add `id-token: write`, delete the secret.
